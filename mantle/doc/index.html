Mantle

A Sparkplug B host application for Ignition. Tags are created as they are born, historized by default, and customized in place — there is no second set of tags to maintain.

What it does

Point Mantle at an MQTT broker. Every Sparkplug edge node publishing to that broker appears as a folder of tags, with the right data types, engineering units, and documentation carried across from the edge. Nothing has to be declared in advance, and nothing has to be re-declared when the edge changes.

Writes go back the other way: writing to a tag sends an NCMD or DCMD to the edge node that owns it.

Customization is safe

A managed tag provider keeps two layers. What Mantle sets is stored under prg; what you set in the Designer sits beside it and wins. So an edge node rebirth refreshes data types, units and the history default without touching an alarm you added, a scale factor you set, or a tag you switched history off on.

A gateway with no tag historian records nothing. Mantle will say so — the connection's Status reads "Connected, but nothing is being recorded" — but it cannot invent a historian. Configure one under Services → Historians, and history switches itself on as each node births again. No tag needs touching.

TLS

Use an ssl:// URL and TLS is on. There is deliberately no truststore setting: the broker's certificate is verified against the gateway's own trust store.

A broker with a certificate from your own CA

Put the CA certificate in the gateway's data/certificates/supplemental/ directory and restart the gateway. Ignition loads everything there into the trust store that Mantle uses, so one CA serves every module on the gateway.

If the certificate is not trusted, the connection says so rather than failing quietly:

Not connected to ssl://broker:8883 — SunCertPathBuilderException:
unable to find valid certification path to requested target

A broker that requires a client certificate

Mutual TLS. Fill in the TLS section of the connection:

Setting
Client CertificatePath to a PEM certificate, or a chain
Client Private KeyPath to the PEM private key, in PKCS#8 format
Client Private Key PasswordOnly if the key is encrypted

Both files are read at connect time, so a renewed certificate is picked up by a reconnect rather than needing the connection edited. If your key is in PKCS#1 form (it begins -----BEGIN RSA PRIVATE KEY-----), convert it:

openssl pkcs8 -topk8 -nocrypt -in client.key -out client.pk8.key

Checking that it is working

Diagnostics → Mantle → Sparkplug shows every connection, the edge nodes and devices under it, and four numbers worth watching:

Counter
MessagesEverything received. Should climb.
Sequence gapsShould be zero. A gap means a message was lost between the edge and the gateway.
Rebirths requestedMantle asking a node to re-announce itself, usually after a gap.
Decode failuresShould be zero. A payload that could not be read.

Each node has a Request rebirth button, which asks that node to publish its birth certificate again — the way to recover a node whose tags look stale or incomplete.

From a script or a monitoring system

The same data is JSON at GET /data/mantle/status, and a rebirth is POST /data/mantle/rebirth/<group>/<edge>. Both accept any authenticated gateway identity, including an API token. Reading needs READ; a rebirth needs WRITE, because it is a command to the field.

Common problems

Tags are not appearing

Check the connection's Status on the configuration page first — a connection that is not connected says why. If it is connected, the edge node may be publishing to a group ID the connection is filtering out, or may not have published a birth certificate yet. Press Request rebirth.

Values are there but history is empty

Either the gateway has no historian (the Status column says so), or Ignition's own sample-rate deadband is discarding them. Ignition stores at most one sample per second by default; a faster process needs HistoryTimeDeadband lowered on the tag or the provider.

A node shows online after it has actually gone

Sparkplug reports a death through the broker's last-will mechanism, which only fires when the broker notices the connection has dropped — up to one keep-alive interval later. A node killed without a clean disconnect takes that long to be marked offline.
